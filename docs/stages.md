# 단계별 구현 — 가상 포트폴리오 수익률 서비스

해설 영상에서 **한 번에 완성하지 않고 세 단계로 나눠** 만들어 가기 위한 코드입니다.
각 단계는 그대로 실행되는 프로젝트이고, 다음 단계는 앞 단계에 얹는 구조입니다.
이 저장소는 세 단계를 **커밋**으로 구분합니다. 태그 `step1` → `step2` → `step3` 순서이고, `step3`가 최종(`main`)입니다.

| 단계 | 커밋(태그) | 한 문장 |
|---|---|---|
| 1 | `step1` | 설계한 흐름이 도는지만 확인합니다. 검증도 예외 처리도 하지 않고, 시세는 요청마다 받아 옵니다. |
| 2 | `step2` | 입력 검증, 에러 응답, 매입가 고정, 수익률 반올림을 채웁니다. 아직 시세는 요청마다 받아 옵니다. |
| 3 | `step3` (= `main` 최신 커밋) | 외부 호출을 요청 경로 밖으로 빼냅니다. 주기 갱신, 토큰 재사용, 장애 대비가 한 번에 풀립니다. |

단계 이동과 단계 간 변경점 확인은 태그로 합니다.

```bash
git checkout step1        # 1단계 코드로 이동 (돌아올 때는 git checkout main)
git diff step1 step2      # 2단계에서 추가된 것
git diff step2 step3      # 3단계(최종)에서 추가된 것
```

각 단계의 코드에는 **그 단계에서 무엇을 만들고 무엇을 일부러 하지 않는지** 설명하는 주석이 붙어 있습니다.
같은 클래스라도 단계마다 주석이 다릅니다. 예를 들어 `Holding`은 1단계에서 담은 시점의 가격을 저장하지 않는 이유와
그래서 수익률이 0으로 남는 과정을 설명하고, 2단계부터는 `purchasePrice` 필드가 매입가 고정을 어떻게 떠받치는지 설명합니다.
아래 표와 함께 읽으면 단계마다 어떤 판단을 했는지 따라갈 수 있습니다.

실행은 어느 단계에서든 같습니다.

```bash
docker run -p 9091:9091 ghcr.io/donghyunkim-hi/portfolio-price-server:1.2.0   # 가상 시세 서버
./gradlew bootRun                                                            # 포트 8080
```

> 아래 표의 값은 모두 전용 시세 서버(관리자 API로 가격 `A001=10000` 고정, 간헐 장애 끔)를 띄우고
> 1단계 8131, 2단계 8232, 3단계 8080 포트로 실제 실행해 2026-11-21에 측정한 값입니다.

## 1단계 — 정상 경로

**만드는 것**: CSV 적재, 상품 목록 조회, 포트폴리오 생성, 조회, 목록, 수정, 삭제.

**일부러 하지 않는 것**: 입력 검증, 에러 응답 형식, 매입가 고정, 수익률 반올림, 주기 갱신, 토큰 재사용, 장애 대비.
시세는 조회할 때마다 시세 서버에서 받아 오고, 매입가는 저장하지 않습니다.

**실행하면 이렇게 됩니다** (실측)

| 확인 | 결과 |
|---|---|
| 상품 목록 `GET /api/v1/products` | 200, 배열로 **80개**. 첫 항목 `{"code":"A001","name":"가상 성장 채권 01","type":"BOND","currentPrice":10000}` |
| 포트폴리오 생성 / 조회 / 목록 / 삭제 | **201 / 200 / 200 / 204** — 흐름 자체는 돕니다 |
| 이름 `""`, `quantity: 0`, 같은 `code` 두 번 | **모두 201** (400이어야 함, 2단계에서 고칩니다) |
| 없는 상품 코드로 생성 | **500** (400 `UNKNOWN_PRODUCT`여야 함) |
| 없는 포트폴리오 조회 | **500** (404 `PORTFOLIO_NOT_FOUND`여야 함) |
| `A001` 10주를 10,000원에 담은 직후 | `totalCost` 100,000 / `totalValue` 100,000 / `profit` **0** / `returnRate` **0** |
| 시세를 11,000으로 바꾼 뒤 같은 포트폴리오 조회 | `purchasePrice`가 **10000에서 11000으로 같이 바뀜**, `totalCost`도 **110,000으로 바뀜**, `returnRate`는 여전히 **0** |
| └ 왜 그런가 | 매입가를 저장하지 않고 조회할 때마다 현재가로 다시 계산하기 때문입니다. 평가금액과 매입금액이 항상 같아서 **수익률이 영원히 0**입니다 |
| 상품 조회 3번 동안 토큰 발급 | **3회** — 요청마다 새로 발급합니다 (3단계에서 고칩니다) |
| 시세 서버 `ALWAYS_503` 중 GET | 상품 조회, 목록, 상세 **전부 500** (GET은 5xx 금지, 3단계에서 고칩니다) |
| `check-scenarios.sh` 전체 | **통과 3 / 실패 5** (S1, S3, S6). 단 S6은 착시다 — 주기 갱신을 만들어서가 아니라 요청마다 시세를 부르기 때문이다 |

> 촬영 포인트: "서버가 뜨고 응답이 온다"와 "요구사항을 만족한다"가 다르다는 것을 여기서 보여 줍니다.
> **가장 강한 장면은 시세를 11,000으로 바꾼 뒤 매입가가 따라 올라가고 수익률이 0으로 남는 화면**입니다.
> 수익률 서비스인데 수익률이 안 나온다는 것이 2단계의 동기가 됩니다.

## 2단계 — 입력 검증과 계산 규칙

**추가하는 것**
- `GlobalExceptionHandler`로 에러 응답 형식(`{"code","message"}`) 통일
  400 `INVALID_REQUEST`, 400 `UNKNOWN_PRODUCT`, 404 `PORTFOLIO_NOT_FOUND`, 503 `PRICE_NOT_READY`
- 입력 검증: 이름 1~50자, `holdings` 1~20개, 같은 코드 금지, `quantity` 1~1,000,000, 존재하는 상품 코드
- 계산 규칙: **매입가를 보유 종목에 저장해 고정**, 수익률 HALF_UP 반올림

**여전히 하지 않는 것**: 30초 주기 갱신, 토큰 재사용, 마지막 시세 보관(장애 대비).
시세는 **요청이 들어올 때마다** 시세 서버에서 받아 옵니다.

**실행하면 이렇게 됩니다** (실측)

| 확인 | 결과 |
|---|---|
| 이름 `""`, `quantity: 0`, 같은 `code` 두 번 | **전부 400 `INVALID_REQUEST`** |
| 없는 상품 코드 | **400 `UNKNOWN_PRODUCT`** (`"존재하지 않는 상품 코드입니다: ZZZZ"`) |
| 없는 포트폴리오 조회 | **404 `PORTFOLIO_NOT_FOUND`** |
| `A001` 10주를 10,000원에 담고 시세를 11,000으로 바꾼 뒤 조회 | `purchasePrice` **10000 유지**, `currentPrice` 11000, `totalCost` **100,000 유지**, `totalValue` **110,000**, `profit` **10,000**, `returnRate` **10.00** |
| 반올림 경계 (매입가 80,000) | 현재가 80,092 → `returnRate` **0.12**(0.115 올림), 현재가 80,091 → **0.11**(0.11375 내림) |
| 상품 조회 3번 동안 토큰 발급 | **3회** — 아직 요청마다 새로 발급합니다 (S7 위반) |
| **시세 서버 `ALWAYS_503` 중 GET** | 상품 조회, 목록, 상세 **전부 500** — 아직 깨집니다 (R6, S8 위반) |
| `GET /api/v1/products` 응답 시간 | **평균 0.178초** (20회 측정, 0.062 \~ 0.286초) |
| `check-scenarios.sh` 전체 | **통과 6 / 실패 2** (S7, S8만 실패) |

> 촬영 포인트: 여기서 시세 서버를 `ALWAYS_FAIL`로 걸고 GET을 쏘아 **직접 500을 내 보이는 것**이 3단계의 동기가 됩니다.
> 평가 기준표에서 장애 중 GET이 5xx를 내는 것은 치명 오류 F2(−10점)입니다.

## 3단계 — 외부 호출을 요청 경로 밖으로 (최종)

**새로 생기는 클래스는 셋뿐입니다.**

| 클래스 | 역할 | 푸는 문제 |
|---|---|---|
| `PriceSnapshotStore` | 마지막으로 성공한 시세 스냅샷 보관 | 장애 중에도 GET이 응답 (R6, S8) |
| `PriceRefreshScheduler` | 30초마다 갱신, 실패하면 예외를 삼키고 `markStale()` | 주기 갱신 (R4, S6) |
| `TokenCache` | 만료 직전까지 토큰 재사용, 401이면 한 번만 재발급 | 토큰 재사용 (R5, S7) |

핵심은 **읽기(요청)와 가져오기(외부 호출)를 떼어 놓는 것**입니다.
2단계까지는 조회 한 번이 외부 호출 두 번이었고, 3단계에서는 조회가 메모리 읽기 한 번이 됩니다.

**실행하면 이렇게 됩니다** (실측)

| 확인 | 결과 |
|---|---|
| 계산 결과 | 2단계와 같습니다 (`totalCost` 100,000 / `totalValue` 110,000 / `profit` 10,000 / `returnRate` 10.00) |
| 시세 변경 반영 | **0~30초** (갱신 주기가 30초라 변경 시점에 따라 달라집니다. 3회 측정 24.0 / 28.0 / 30.0초. S6 기준 45초는 항상 통과) |
| 토큰을 강제 만료시킨 뒤 시세 변경 | 갱신이 계속됩니다. **28초**에 반영 (S7) |
| 토큰 발급 횟수 대비 시세 호출 횟수 | 토큰 **2회** 대비 시세 조회 **4~5회** — 재사용하고 있습니다 |
| 시세 서버 `ALWAYS_503` 중 GET | 상품 조회, 목록, 상세 **전부 200** |
| 장애 중 상세 응답 | 다음 갱신이 실패해야 알 수 있으므로 최대 30초 뒤 `"priceStale": true`로 바뀝니다 (가정 G1) |
| `GET /api/v1/products` 응답 시간 | **평균 0.003초** (20회 측정, 0.002 \~ 0.019초. 2단계는 평균 0.178초) |
| `check-scenarios.sh` 전체 | **통과 8 / 실패 0** |

> 촬영 포인트: 2단계로 되돌려 같은 `ALWAYS_FAIL` 명령을 다시 실행하면 500과 200이 바로 대비됩니다.
> 응답 시간 차이(평균 0.178초에서 0.003초, 각 20회 측정)도 같은 화면에서 보여 줄 수 있습니다.

## 세 단계를 각각 실행해 측정한 시나리오 표

| | 시나리오 | 1단계 | 2단계 | 3단계 |
|---|---|---|---|---|
| S1 | 상품 목록 조회 | ○ | ○ | ○ |
| S2 | 포트폴리오 생성, 조회, 삭제와 입력 검증 | ✕ | **○** | ○ |
| S3 | 포트폴리오 목록 | ○ | ○ | ○ |
| S4 | 매입가 고정 | ✕ | **○** | ○ |
| S5 | 평가 계산 (수익률 반올림) | ✕ | **○** | ○ |
| S6 | 시세 주기 갱신 (45초 안 반영) | △ (착시) | △ (착시) | **○** |
| S7 | 토큰 만료 — 갱신 지속 + 매번 발급 금지 | ✕ | ✕ | **○** |
| S8 | 시세 서버 장애 중 GET이 5xx 없이 응답 | ✕ | ✕ | **○** |
| | **통과 수** | **3** | **6** | **8** |

**△는 통과했지만 맞아서 통과한 것이 아닙니다.**

S6은 1·2단계에 주기 갱신이 없는데도 통과합니다. 조회할 때마다 외부를 부르기 때문에 항상 최신일 뿐이고,
그 대가로 S8이 깨지고 토큰이 요청마다 발급됩니다. 3단계에서 주기 갱신을 넣고도 45초 안에 반영되어야 진짜 통과입니다.

> 촬영에서 꼭 짚을 지점입니다. **항상 최신이면 좋은 것 아닌가에 대한 답이 S7과 S8입니다.**

### 시세 서버를 쓸 때 주의할 점

- 가상 시세 서버는 **기본 설정에서 간헐적으로 503을 반환합니다**(기본 장애율 5%).
  1·2단계는 외부 호출이 요청 경로 안에 있어서, 장애를 걸지 않아도 이 확률만큼 GET이 500이 납니다.
- 촬영 중 값을 고정하려면 관리자 API를 씁니다 (헤더 `X-Admin-Token` 필요). **초기화를 항상 맨 앞에** 두고, 그다음 장애를 끄고, 그다음 가격을 고정합니다.
  ```bash
  curl -X POST localhost:9091/admin/reset   -H 'X-Admin-Token: admin-secret'
  curl -X POST localhost:9091/admin/failure -H 'X-Admin-Token: admin-secret' \
       -H 'Content-Type: application/json' -d '{"mode":"NONE","transientFailureRate":0}'
  curl -X POST localhost:9091/admin/prices  -H 'X-Admin-Token: admin-secret' \
       -H 'Content-Type: application/json' -d '{"prices":{"A001":10000},"freeze":true}'
  ```
  `POST /admin/reset`은 **장애율을 기본값 5%로 되돌리므로** 초기화한 뒤에는 장애 끄기를 다시 보내야 합니다.
  `freeze: true`는 **지정한 코드만** 고정합니다. 나머지 79개는 30초마다 계속 바뀌므로, 상품 목록을 화면에 펼쳐 보일 때 지정하지 않은 상품의 `currentPrice`가 움직이는 것은 정상입니다.
- **가격을 고정한 뒤 약 35초를 기다려야** 구현한 서버의 스냅샷에 그 값이 들어옵니다(3단계 기준). 담기 전에 이 대기를 넣지 않으면 매입가가 엉뚱한 값으로 잡힙니다.
